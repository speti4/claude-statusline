# Deglobalize the `/statusline` skill

**Branch:** `deglobalize-statusline-skill`
**Status:** done
**Date:** 2026-09-07

## Context

The `/statusline` skill currently lives in the global scope (`~/.claude/skills/statusline/`),
so it is loaded into the context of every Claude Code session on this machine. The user
configured the statusline once and rarely changes it; when they do, they are working in
either `claude-setup` or `claude-statusline`. There is no reason for it to hang in every
session's context.

Decision: the skill leaves the global scope and becomes a **project-level** skill in two
repos — `claude-statusline` (source of truth) and `claude-setup` (synced copy). The deploy
scripts must stop putting it back into `~/.claude/`.

Coordinated with a parallel session working in `E:\projects\claude-setup`, which owns
everything outside this repo: deleting the stale global copy, `scripts/sync-statusline-skill.ps1`,
and the `claude-setup` side docs.

**Order of operations:** this repo first → global copy deleted → `claude-setup` takes the
finished files as its copy.

## What stays the same

`~/.claude/statusline.py` **remains deployed**. The `settings.json` statusline command runs
it; only the *skill* leaves the global scope. The deploy scripts keep copying `statusline.py`
and drop only the skill copy.

## Design decisions

### `set_style.py` writes both copies (dual-write)

The skill's whole value is instant effect: you type `/statusline powerline` and the bar
changes. That requires writing `~/.claude/statusline.py`, because that is what
`settings.json` runs. Writing only a repo-local copy would make the command look broken.

So: **always** write `~/.claude/statusline.py`, and **additionally** write the repo-root
`statusline.py` when it exists. Detection is relative to `__file__` (not cwd — the skill can
be invoked from any subdirectory, and cwd-based detection silently picks the wrong target):

```
skill_dir = dirname(realpath(__file__))          # <repo>/.claude/skills/statusline
repo_root = skill_dir/../../..                   # <repo>
local     = repo_root/statusline.py
```

Guard: only write `local` if it exists **and** contains `COLOR_SCHEME = "` — so an unrelated
file of the same name in another repo is never clobbered.

Behaviour:
- **claude-setup**: no `statusline.py` at repo root → writes only `~/.claude/statusline.py`
  (identical to today's behaviour).
- **claude-statusline**: writes both → the bar updates immediately *and* the repo source
  stays current. **This removes the drift problem documented in CLAUDE.md.**

The file is byte-identical in both repos — no per-repo branching.

### `python` → `python3`

`deploy.sh` currently rewrites `python` → `python3` in the deployed `SKILL.md` because macOS
has no `python`. Once the skill is no longer deployed, that hack has no target and the
committed `SKILL.md` would break `/statusline` on the MacBook (this repo is used from two
machines). Verified `python3 -V` → `Python 3.14.3` on this Windows box (Python Manager shim),
so a single committed `python3` works on both platforms. The rewrite block is removed.

Machine-level dependency: the Windows `python3` shim must stay installed. Documented on the
`claude-setup` side (`docs/environment.md`).

### Source-of-truth marker

Neutral wording so it is true in both repos and the two copies stay byte-identical:
`Source of truth: claude-statusline — the claude-setup copy is generated by scripts/sync-statusline-skill.ps1`

## Steps

- [x] 1. `git mv skills/statusline` → `.claude/skills/statusline/` (the repo already has
      `.claude/skills/deploy/`; `skills/` stops being a deploy source, so a second copy
      would only invite drift). The now-empty `skills/` directory is gone.
- [x] 2. `set_style.py`: dual-write with the `__file__`-relative guard; reports how many files
      were written; source-of-truth comment header added
- [x] 3. `SKILL.md`: `python` → `python3` in the body *and* in `allowed-tools`;
      source-of-truth marker as a one-line HTML comment after the frontmatter;
      `version: 3.1.0` → `4.0.0`
- [x] 4. `scripts/deploy.ps1` + `scripts/deploy.sh`: skill copy and `python3` rewrite block
      dropped; only `statusline.py` is deployed
- [x] 5. `.claude/skills/deploy/SKILL.md`: description updated, `version: 1.1.0` → `2.0.0`
- [x] 6. `CLAUDE.md`: drift section replaced with a description of the dual-write; Scope and
      Runtime Deployment paths updated
- [x] 7. `README.md`: file table, deploy section, Configure section, Development section
- [ ] 8. **Handed off.** `.claude/settings.local.json` still holds the stale
      `Bash(python *set_style.py)` allow rule; the new command is `python3`. It is a
      permission file and this task reached this repo through a peer session, so broadening
      the rule was not mine to do. The user handed the item to the `claude-setup` session to
      settle with them. Until it is updated, the first `/statusline` run raises one
      permission prompt — that is this rule, not a `${CLAUDE_SKILL_DIR}` resolution failure.
      (The file is untracked, globally gitignored.)

### Not in scope
No `.gitattributes` pin for the skill files. The CRLF risk it would have covered is handled
on the `claude-setup` side instead (normalize-on-write plus a directory-local `.gitattributes`
there), so this repo's line-ending policy stays untouched.

## Handoff

The `claude-setup` session deleted the global `~/.claude/skills/statusline/` and built
`scripts/sync-statusline-skill.ps1` (fixed file list: `SKILL.md`, `set_style.py`;
CRLF→LF on write; SHA256 compare). Notify it once these files are final so it can re-run
the sync against the finished versions.
